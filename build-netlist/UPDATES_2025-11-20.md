# Build-Netlist Skill Updates (2025-11-20)

## Summary

Updated the build-netlist skill to use **more flexible and precise terminology** that captures the underlying problem (floating nodes) rather than a rigid rule about "two sides." Also added **explicit NC (no-connect) naming conventions** to distinguish between deliberately unconnected terminals and accidentally floating nodes.

## Key Changes

### 1. Rule 2 Reframed: From "Two Sides" to "All Terminals"

**Old formulation:**
> "Every component has two sides. Don't leave components half-traced."

**New formulation:**
> "Document all terminals of every component. Every terminal must either be: (1) connected to a named node, (2) deliberately NC with unique name, or (3) tied to power/ground explicitly."

**Why this matters:**
- Applies correctly to components with >2 terminals (BJTs with 3 pins, MOSFETs with 4, ICs with N pins)
- Captures the **underlying problem**: floating nodes break SPICE simulations
- Clarifies the solution: no undocumented pads, period

### 2. Unique NC (No-Connect) Naming Convention

**Problem solved:**
- Distinguish between **deliberately unconnected** pads (by design) and **accidentally floating** nodes (errors)
- Prevent generic NC names that lose component context

**Solution:**
- Deliberately unconnected: Use unique functional names like `NC_U1_PIN7`, `NC_R5_PAD2`, `NC_TESTPOINT_TP5`
- Floating node errors: Mark as `FLOATING_[description]` during fix-up, then trace and resolve
- Never use generic: Avoid `NC`, `NC1`, `NC2`

**Examples:**
```spice
R5 +5V_RAIL NC_R5_PAD2 10k      ; R5 pad 2 is intentionally unconnected
U1 GND NC_U1_PIN7 ... ...        ; U1 pin 7 marked NC on datasheet
Q7 C_RAIL Q7_GATE Q7_SOURCE ... ; All three terminals connected
```

## Rationale

The original Rule 2 ("Every component has two sides") was a **proxy for the real rule**, which is about preventing floating nodes. By reframing around the underlying problem and the solution (systematic terminal documentation), the skill now:

1. **Applies correctly to all component types** (not just passive two-terminal components)
2. **Captures the real error** (floating nodes cause simulation failure) not a symptom
3. **Provides explicit guidance** for edge cases (unpopulated footprints, NC pins, test points)
4. **Distinguishes intentions** (deliberate NC vs accidental floating) which is crucial for circuit design

The NC naming convention `NC_[COMPONENT]_[PAD]` makes it immediately obvious:
- **Which component** is affected
- **Which terminal/pad** is unconnected
- **That this is intentional** (not an oversight)

This prevents issues where generic NC names hide which component was meant, and makes it clear in the netlist that the designer/tracer deliberately left something unconnected (not accidentally forgot to document it).

## No Breaking Changes

These updates are **backwards compatible**. Existing netlists with two-terminal components continue to work. The changes simply extend the framework to handle:
- Multi-terminal components clearly
- Intentional NC pads with proper naming
- Better error detection (floating vs deliberate NC)

## Next Steps

When using the skill going forward:
1. Check every component terminal (not just "both sides")
2. Use unique NC names for intentionally unconnected pads
3. Document which terminals are connected, NC, or power/ground
4. Use `FLOATING_[name]` temporarily for undocumented terminals while tracing
5. Validate against error-handling protocol for NC vs floating distinction
